# AGENTS.md

## Project Goal
Build a transcription platform with:
- `Next.js` frontend for upload, job tracking, and transcript viewing
- `FastAPI` backend for auth, job creation, and result delivery
- `Redis` queue plus Python worker for asynchronous transcription
- `PostgreSQL` for application data
- `S3-compatible storage` or local disk for uploaded media
- fully local transcription processing with no required cloud speech API
- development on a `MacBook Air M4`
- transcription execution on a separate `Windows PC with RTX 3070`

The system should be designed for long-running transcription jobs. Do not perform full transcription work inside the synchronous API request path.

## Default Stack
- Frontend: `Next.js` + `TypeScript`
- Backend API: `FastAPI`
- Worker: `Celery` or `RQ`
- Queue/Broker: `Redis`
- Database: `PostgreSQL`
- Storage: local disk in dev, `S3-compatible` storage in production
- Speech-to-text engine: local `faster-whisper`

## Environment Profile

### Development Machine
- Primary development machine: `MacBook Air M4`
- Use the Mac for:
  - frontend development
  - FastAPI development
  - database migrations
  - local API testing
  - light end-to-end integration testing
- Do not rely on the MacBook Air M4 for production-grade transcription throughput.

### Transcription Worker Machine
- Dedicated transcription machine: `Windows PC with RTX 3070`
- Use the Windows machine for:
  - `Redis`-backed worker execution
  - local `faster-whisper` GPU inference
  - heavy transcription jobs
- The worker may run on the same local network during development, and later be exposed or relocated for public deployment.

## High-Level Architecture
1. The frontend uploads an audio or video file.
2. The FastAPI API validates the request and stores the media file.
3. The API creates a `transcription_jobs` record with status `pending`.
4. The API enqueues a background job in `Redis`.
5. The Windows RTX 3070 worker pulls the job, runs transcription, and stores the result.
6. The worker updates the job status to `completed` or `failed`.
7. The frontend polls or refreshes the job detail endpoint until the result is ready.

## Deployment Topology

### During Development
- `frontend` runs on the MacBook Air M4
- `FastAPI API` runs on the MacBook Air M4
- `PostgreSQL` and `Redis` may run locally on the MacBook Air M4
- transcription jobs are executed by the Windows RTX 3070 worker over the local network

### For Public Deployment
- the frontend and FastAPI API may be deployed to a public server
- the Windows RTX 3070 machine can remain the transcription worker if network access is configured securely
- later, the worker can be moved to a dedicated Linux GPU server without changing the application contract

## Core Principles
- Keep the API stateless where practical.
- Use async job processing for transcription and other heavy tasks.
- Treat `PostgreSQL` as the source of truth for job state.
- Store uploaded media outside the database.
- Keep speech-to-text engine access behind a service abstraction so engines can be swapped later.
- Prefer small, composable modules over large route or service files.
- Keep transcription execution local to the machine or local network environment.
- Design the system so the API and worker can run on separate machines.
- Keep the worker transport and file access strategy explicit so the Windows worker can process jobs generated by the Mac or public API server.

## Backend Responsibilities

### FastAPI API
Responsible for:
- authentication and session handling
- file upload endpoints
- transcription job creation
- job status lookup
- transcript retrieval and export

Suggested endpoints:
- `POST /auth/register`
- `POST /auth/login`
- `POST /transcriptions/upload`
- `GET /transcriptions/{job_id}`
- `GET /transcriptions/{job_id}/result`
- `GET /transcriptions/{job_id}/download`
- `DELETE /transcriptions/{job_id}`
- `GET /health`

### Worker
Responsible for:
- fetching queued jobs
- loading the media file from storage
- running transcription
- optional post-processing such as timestamps, cleanup, or segment formatting
- storing transcript output
- updating job status and error details

The worker is expected to run on the Windows RTX 3070 machine by default.

### Speech-to-Text Service Layer
Create a stable interface like:
- `transcribe(file_path, language=None, speaker_labels=False) -> TranscriptResult`

Implementations can include:
- `whisper_engine.py`
- `faster_whisper_engine.py`

Do not couple route handlers directly to one transcription backend.
Do not make external speech API calls unless the user explicitly changes this requirement.
Prefer a provider implementation optimized for `CUDA` execution on the Windows worker.

## Frontend Responsibilities

### Main Views
- `login/register`
- `dashboard`
- `jobs list`
- `job detail`
- `settings`

### UX Flow
1. User uploads a file.
2. Frontend sends multipart request to the backend.
3. Backend returns `job_id`.
4. Frontend redirects to the job detail page.
5. Frontend polls the job endpoint for status updates.
6. Once complete, frontend displays transcript text, segments, timestamps, and download actions.

### Frontend Rules
- Keep API access in a dedicated client module.
- Use typed request and response models.
- Separate upload UI, job list UI, and transcript viewer into focused components.
- Prefer `TanStack Query` for server-state handling.
- Treat transcription as asynchronous and never assume immediate completion.

## Database Setup

Use `PostgreSQL` as the primary relational database.

During development on the MacBook Air M4:
- run a local PostgreSQL instance
- create one application database, for example `transcribe_db`
- point both the FastAPI app and the worker to the same database

The database stores:
- user accounts
- transcription job state
- transcript output
- application metadata

The database does not store:
- uploaded audio binaries
- uploaded video binaries
- large raw media payloads

## ORM And Migration Stack

Use:
- `SQLAlchemy` for ORM models
- `Alembic` for schema migrations

This is the FastAPI equivalent of Django's model plus migration workflow.

Recommended backend structure:

```text
backend/
  app/
    db/
      base.py
      session.py
    models/
      user.py
      transcription_job.py
      transcript.py
  alembic/
  alembic.ini
```

## Migration Workflow

Agents should treat migrations like this:

1. Create or update SQLAlchemy models in `backend/app/models/`
2. Ensure the models are imported into the SQLAlchemy metadata registry
3. Generate a migration with Alembic
4. Apply the migration to PostgreSQL

Equivalent mental mapping from Django:

- Django `python manage.py makemigrations`
  maps to
  `alembic revision --autogenerate -m "message"`

- Django `python manage.py migrate`
  maps to
  `alembic upgrade head`

Typical commands:

```bash
alembic revision --autogenerate -m "create initial tables"
alembic upgrade head
```

## Model Authoring Rules

- Keep ORM models in `backend/app/models/`
- Use one model file per major table when practical
- Register all models in a shared metadata base
- Do not mix Pydantic request schemas with ORM model classes
- Add explicit foreign keys and indexes
- Use migration files for schema changes instead of calling `create_all()` in production flows

## Initial Database Responsibility

Before application features are implemented, the user should:
- create the PostgreSQL database itself
- configure `DATABASE_URL`

After that, agents should:
- define SQLAlchemy models
- generate Alembic migrations
- apply migrations to create the tables

This means:
- PostgreSQL creates the database container
- Alembic creates and updates the tables inside that database

## Status Model
Use explicit status values:
- `pending`
- `processing`
- `completed`
- `failed`

Optional later:
- `queued`
- `cancelled`

## Implementation Rules For Agents
- Do not add synchronous transcription inside request handlers.
- Do not store large binary uploads in `PostgreSQL`.
- Do not hardcode cloud STT APIs across the codebase.
- Keep configuration in environment variables.
- Add migrations for schema changes.
- Add tests for route behavior, service logic, and worker flow where practical.
- Preserve separation between API schemas, ORM models, and business logic.
- Default to local inference using `faster-whisper` or equivalent local model runtime.
- Assume the MacBook Air M4 is the primary development environment.
- Assume the Windows RTX 3070 machine is the default GPU worker target.
- Avoid Mac-specific GPU assumptions for transcription code paths.
- Keep paths, queue configuration, and storage access portable across macOS and Windows.

- `DATABASE_URL`

- `STORAGE_BACKEND`
- `STORAGE_BUCKET`

- `WHISPER_COMPUTE_TYPE`
- `WORKER_NAME`
- `WORKER_PLATFORM`

- `PUBLIC_MEDIA_BASE_URL`

If API and worker run on different machines, ensure uploaded media is accessible by both sides through one of these approaches:
- shared storage
- object storage
- API-mediated download for worker pickup

Do not assume local filesystem paths on the Mac are directly readable by the Windows worker.

## MVP Scope
The first working version should support:
- user registration and login
- single-file upload
- async transcription
- job status polling
- transcript result view
- transcript download in `txt` and `json`
- fully local speech-to-text processing
- separate API and GPU worker execution across Mac and Windows machines

Avoid building advanced features first unless explicitly requested:
- real-time websocket transcription
- collaborative editing
- speaker diarization
- billing
- admin analytics

## Definition Of Done
A task is considered complete when:
- the user can upload a media file from the frontend
- the backend stores the file and creates a job
- the Windows RTX 3070 worker processes the job asynchronously
- the transcript is persisted and retrievable
- the frontend shows live job status and final transcript
